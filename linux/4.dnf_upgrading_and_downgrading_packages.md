# DNF Upgrading And Downgrading Packages

## What This Is About

This note explains how to update packages with DNF and how to downgrade a package when an application requires an older version.

Main idea:

```text
Use dnf upgrade to install available updates.
Use dnf downgrade only when you have a real compatibility reason.
```

## Upgrade All Packages

To install all available updates:

```bash
sudo dnf upgrade #will upgrade ALL installed packages that have available updates from the enabled repositories.
```

`dnf update` usually works too, but `upgrade` is the preferred command.

Important detail:

```text
dnf update is basically an alias/reference to dnf upgrade.
```

So prefer:

```bash
sudo dnf upgrade
```

## What DNF Upgrade Does

When running:

```bash
sudo dnf upgrade
```

DNF will:

- check repository metadata
- refresh repository indexes if needed
- calculate available updates
- install all possible updates

If everything is already current, DNF may show:

```text
Nothing to do.
```

Meaning:

```text
No package updates are currently available.
```

## Are Updates Safe?

Usually updates should be safe on:

- Red Hat Enterprise Linux
- CentOS Stream / CentOS, depending on version and repository setup

This is because enterprise Linux distributions usually do not upgrade software to completely new major versions during one OS release.

Example:

```text
Red Hat Enterprise Linux 9 will usually keep the same main package versions.
It receives security fixes, bug fixes, and minor fixes.
It does not suddenly upgrade everything to the latest upstream versions.
```

Large version changes usually happen when upgrading the operating system release itself.

Example:

```text
RHEL 9.1 -> RHEL 9.2       minor OS release update
RHEL 8 -> RHEL 9           major OS release upgrade
```

Fedora is different.

Fedora is more cutting edge, so newer package versions appear more often and update-related issues are more likely.

## Why Downgrades Sometimes Matter

Most of the time, we should keep packages updated.

But sometimes an application does not work with a newer package version.

Examples:

- an application expects an older Python patch version
- a proprietary tool only supports a specific PHP version
- encrypted PHP code requires a specific loader that only supports older PHP
- a vendor application has not certified the newer package yet

In that case, a package downgrade may be required.

## Check Current Package Version

Example with Python:

```bash
python3 --version
```

Example output:

```text
Python 3.9.16
```

This means the installed Python 3 package currently provides Python version `3.9.16`.

Your version may be different.

## Downgrade A Package

Basic syntax:

```bash
sudo dnf downgrade PACKAGE
```

Example:

```bash
sudo dnf downgrade python3
```

DNF will calculate whether an older available version can be installed.

Example result:

```text
Downgrading:
  python3  3.9.16 -> 3.9.14
```

Before confirming, read the transaction carefully.

Only continue if the downgrade list is safe.

## Packages You Should Not Downgrade

Some packages are too central to the system.

Do **not** downgrade these:

```text
dbus -> is a system messaging service. It lets programs and system services communicate with each other.

glibc -> means GNU C Library. It is one of the most important libraries on a Linux system. Almost every normal Linux program depends on it, directly or indirectly. It provides basic functions

selinux-policy -> contains SELinux security rules. SELinux controls what processes are allowed to do.
```

Why:

```text
Many system services and programs depend on them.
Downgrading them can break the whole system.
```

If DNF proposes downgrading any of these packages, refuse the transaction.

Also avoid downgrading the whole OS to a previous minor version.

Bad idea:

```text
CentOS 9.2 -> CentOS 9.1
RHEL 9.2 -> RHEL 9.1
```

Downgrading one normal application package can be acceptable.

Downgrading core system packages or the whole OS release is risky.

## Why RHEL And CentOS Do Not Always Use Latest Versions

Enterprise Linux repositories usually keep stable package versions.

Example:

```text
Python 3.9.x may stay as the default Python version for the OS release.
```

Even if newer Python versions exist upstream, the repository may only provide updates inside the same supported version family. So NOT MAJOR updates will be performed with dnf upgrade!

For example:

```text
Python 3.9.10
Python 3.9.14
Python 3.9.16
```

But not automatically:

```text
Python 3.10
Python 3.11
Python 3.12
```

This is not because DNF cannot upgrade packages to newer versions.

It is because DNF installs what the configured repositories provide.

Repository policy controls what versions are available.

## List Available Package Versions

To show available versions of a package:

```bash
sudo dnf list python3 --showduplicates
```

Meaning:

```text
Show python3 packages.
Also show duplicate package names with different available versions.
```

Example output may show multiple versions:

```text
python3.x86_64  3.9.10-2.el9
python3.x86_64  3.9.14-1.el9
python3.x86_64  3.9.16-1.el9
```

The exact versions and CPU architecture may be different on your system.

### Architecture examples:

```text
x86_64
aarch64
```
`x86_64` and `aarch64` are CPU architecture names.

They describe what kind of processor the package was built for.

`x86_64`

This means 64-bit Intel/AMD architecture.

Common on:

```text
Intel servers
AMD servers
most traditional laptops/desktops
many virtual machines
```

Examples:

```text
Intel Xeon
Intel Core i5/i7/i9
AMD EPYC
AMD Ryzen
```

If your machine is a normal Intel/AMD Linux server, it is probably x86_64.

`aarch64`

This means 64-bit ARM architecture.

Common on:

```text
ARM servers
Raspberry Pi 64-bit OS
AWS Graviton instances
Apple Silicon Linux VMs
some embedded systems
```

Examples:

```text
AWS Graviton
Ampere Altra
Apple M1/M2/M3 running Linux VM
Raspberry Pi 4/5 with 64-bit Linux
```

### Why it matters

DNF packages are built for specific architectures.

Example:

```text
python3.x86_64
python3.aarch64
```

Both may be the same software, but compiled for different CPU types.


## Downgrade To A Specific Version

If multiple versions are available, you can request a specific one.

General syntax:

```bash
sudo dnf downgrade PACKAGE-VERSION
```

Example:

```bash
sudo dnf downgrade python3-3.9.10-2.el9
```

DNF will try to install that exact available version.

Important:

```text
This only works if that version still exists in an enabled repository.
```

If the older version was removed from the repositories, DNF cannot downgrade to it directly.

## Verify After Downgrade

After downgrading Python:

```bash
python3 --version
```

Example output:

```text
Python 3.9.10
```

This confirms the active Python version changed.

## The Problem After Downgrading

After a package is downgraded, the next upgrade may try to install the newer version again.

Example:

```bash
sudo dnf upgrade
```

DNF may propose:

```text
Upgrade python3 3.9.10 -> 3.9.16
```

This is expected.

DNF sees that a newer allowed package version is available.

So a downgrade alone is temporary unless you also prevent that package from being upgraded again.

That topic is usually handled with package version locking or excluding packages from upgrades.

## Practical Example

Problem:

```text
Application works with Python 3.9.10.
Application fails with Python 3.9.16.
```

Check current version:

```bash
python3 --version
```

List available versions:

```bash
sudo dnf list python3 --showduplicates
```

Downgrade to the required version:

```bash
sudo dnf downgrade python3-3.9.10-2.el9
```

Check the transaction before confirming.

Do not continue if DNF wants to downgrade core packages such as:

```text
dbus
glibc
selinux-policy
```

Verify:

```bash
python3 --version
```

## Main Commands

Upgrade all packages:

```bash
sudo dnf upgrade
```

Older equivalent command:

```bash
sudo dnf update
```

Downgrade package to the best available older version:

```bash
sudo dnf downgrade python3
```

List available package versions:

```bash
sudo dnf list python3 --showduplicates
```

Downgrade to a specific version:

```bash
sudo dnf downgrade python3-3.9.10-2.el9
```

Check Python version:

```bash
python3 --version
```

## How To Read DNF Downgrade Output

Before pressing `y`, check:

```text
Which packages will be downgraded?
Are only the expected packages listed?
Are dbus, glibc, or selinux-policy listed?
Will this affect a production application or system service?
Is the older version really required?
```

If unsure, stop and investigate.

## Summary

Use:

```bash
sudo dnf upgrade
```

to install all available updates.

Updates on RHEL and CentOS are usually stable because repositories normally provide security fixes and bug fixes instead of sudden major version jumps.

Use:

```bash
sudo dnf downgrade PACKAGE
```

only when a package version causes a real compatibility problem.

Never downgrade:

```text
dbus
glibc
selinux-policy
```

Important habit:

```text
Always read the full DNF transaction before confirming.
```

After a downgrade, remember:

```text
The next dnf upgrade may upgrade the package again.
```

To keep the older version, you need an additional mechanism such as version locking or package exclusion.
