# DNF Preventing Package Upgrades

## What This Is About

This note explains how to prevent selected packages from being upgraded by DNF.

Main idea:

```text
Usually we should install updates.
Sometimes we need to temporarily or permanently block updates for a specific package.
```

Blocking package upgrades should be an exception, not the normal approach.

## Why Prevent A Package Upgrade?

There are valid reasons to stop one package from being upgraded.

Examples:

- a newer package version is not compatible with an application
- the application was only tested against an older version
- proprietary plugins only support one exact package version
- a vendor has not certified the newer version yet
- a manually compiled kernel module requires the current kernel version
- a package was downgraded manually and should not be upgraded again immediately

## Compatibility Problems

Usually minor package updates should not break applications.

But sometimes they do.

Example:

```text
Application works with Python 3.9.10.
Application fails with Python 3.9.16.
```

In that case, you may need to block the Python upgrade until the application is tested or fixed.

## Tested Versions

Sometimes reliability is more important than immediately installing a newer bug fix.

Example:

```text
An embedded device runs a tool at a tested version.
The device is hard to access physically.
An unexpected software problem would be difficult to fix quickly.
```

In that case, an organization may decide to keep one specific package version for a while.

This should still be reviewed regularly.

## Proprietary Plugins

Some proprietary tools or plugins only support exact versions.

Example:

```text
Plugin supports PHP 8.1.12.
Plugin does not support PHP 8.1.13 or PHP 8.2.
```

Sometimes the code even allow-lists only specific versions.

Meaning:

```text
The software checks the version.
If the version is not on the allowed list, it refuses to run.
```

In that case, you may be forced to wait for the third-party vendor.

## Kernel Modules

The kernel is the core of the operating system.

Sometimes systems use manually compiled kernel modules.

This can happen with:

- exotic hardware
- vendor drivers
- hardware not supported out of the box
- special storage or network drivers

If the kernel is upgraded automatically, the manually compiled module may no longer work.

So some systems temporarily block kernel upgrades until the module can be rebuilt and tested.

## Temporary Exclude During One Upgrade

To exclude a package from one upgrade transaction, use:

```bash
sudo dnf upgrade --exclude=PACKAGE
```

Example:

```bash
sudo dnf upgrade --exclude=python3
```

Meaning:

```text
Upgrade the system, but do not upgrade python3 in this transaction.
```

This is temporary.

It only affects this one command.

The next normal upgrade can still upgrade the package:

```bash
sudo dnf upgrade
```

## Excluding Related Packages

Sometimes excluding only one package is not enough.

Example:

```bash
sudo dnf upgrade --exclude=python3
```

DNF may still try to upgrade related packages such as:

```text
python3-libs
python3-tkinter
python-unversioned-command
```

That can cause dependency problems.

In that case, exclude all related packages from the transaction:

```bash
sudo dnf upgrade --exclude=python3,python3-libs,python3-tkinter,python-unversioned-command
```

Meaning:

```text
Upgrade everything possible, but keep these Python-related packages at their current versions.
```

If all pending updates were only for those excluded packages, DNF may show:

```text
Nothing to do.
```

## Important Syntax Detail

Use commas between package names:

```bash
sudo dnf upgrade --exclude=package1,package2,package3
```

You can also repeat the option:

```bash
sudo dnf upgrade --exclude=package1 --exclude=package2 --exclude=package3
```

The comma style is shorter when excluding many related packages.

## Exclude With Wildcards

Sometimes a wildcard is useful.

Example:

```bash
sudo dnf upgrade --exclude='python3*'
```

Meaning:

```text
Exclude packages whose names start with python3.
```

The quotes are important because the shell may try to expand `*` before DNF sees it.

Use wildcards carefully.

They can exclude more packages than intended.

## Permanent Exclude In DNF Config

For a permanent exclude, edit:

```text
/etc/dnf/dnf.conf
```

Add an exclude line under the main configuration section.

Example:

```ini
[main]
exclude=python3 python3-libs python3-tkinter python-unversioned-command
```

Meaning:

```text
DNF should not upgrade these packages during normal operations.
```

This affects future DNF commands until the exclude is removed.

## Temporary vs Permanent Exclude

Temporary exclude:

```bash
sudo dnf upgrade --exclude=python3
```

Use when:

```text
You only need to skip the package once.
You expect to test or fix the application soon.
```

Permanent exclude:

```text
/etc/dnf/dnf.conf
```

Use when:

```text
The package must stay blocked across many upgrades.
You have a clear operational reason.
You will review the decision regularly.
```

## Version Lock Plugin

DNF also has a plugin for version locking packages.

Package name is commonly:

```text
python3-dnf-plugin-versionlock
```

or on some systems:

```text
dnf-plugins-core
```

After installing the plugin, commands are usually like:

```bash
sudo dnf versionlock add PACKAGE
```

Remove a lock:

```bash
sudo dnf versionlock delete PACKAGE
```

List locks:

```bash
sudo dnf versionlock list
```

This can be easier than manually editing `/etc/dnf/dnf.conf` if you routinely lock package versions.

Check the manual on your system:

```bash
man dnf-versionlock
```

or:

```bash
dnf versionlock --help
```

## Dependency Risk

Preventing package upgrades can cause dependency issues.

Example:

```text
Package A is held back.
Package B wants a newer version of Package A.
DNF cannot satisfy both requirements.
Upgrade fails or packages are skipped.
```

This becomes more likely the longer a package is blocked.

Why:

```text
The rest of the system moves forward.
The locked package stays old.
Other packages may eventually require newer dependencies.
```

## Best Practice

Review excluded or locked packages regularly.

Ask:

```text
Is this package still required at the old version?
Can the application now support the newer version?
Is the vendor plugin updated?
Are we missing security updates?
Will this block a larger system upgrade?
```

Remove excludes when they are no longer necessary.

## Before Large System Upgrades

Before a large OS upgrade, remove or review all package excludes and locks.

Examples:

```text
CentOS 8 -> CentOS 9
RHEL 8 -> RHEL 9
```

Why:

```text
DNF needs flexibility during large upgrades.
Locked or excluded packages can block dependency resolution.
```

The fewer packages are locked, the closer the system stays to the repository maintainer state.

That usually means fewer upgrade problems.

## Practical Example

Problem:

```text
Python was downgraded.
The next dnf upgrade wants to upgrade Python again.
The application has not been tested with the newer Python package yet.
```

First inspect the upgrade:

```bash
sudo dnf upgrade
```

If DNF proposes Python-related upgrades, stop with:

```text
n
```

or interrupt carefully with:

```text
Ctrl + C
```

Then run upgrade again with excludes:

```bash
sudo dnf upgrade --exclude=python3,python3-libs,python3-tkinter,python-unversioned-command
```

This allows other package updates while holding back the Python-related packages.

## Main Commands

Temporary exclude one package:

```bash
sudo dnf upgrade --exclude=python3
```

Temporary exclude multiple packages:

```bash
sudo dnf upgrade --exclude=python3,python3-libs,python3-tkinter,python-unversioned-command
```

Temporary exclude with wildcard:

```bash
sudo dnf upgrade --exclude='python3*'
```

Permanent exclude file:

```text
/etc/dnf/dnf.conf
```

Example permanent exclude:

```ini
[main]
exclude=python3 python3-libs python3-tkinter python-unversioned-command
```

Version lock add:

```bash
sudo dnf versionlock add python3
```

Version lock remove:

```bash
sudo dnf versionlock delete python3
```

Version lock list:

```bash
sudo dnf versionlock list
```

## How To Read DNF Output

Before confirming an upgrade with excludes, check:

```text
Are the intended packages really excluded?
Are there dependency problems?
Is DNF skipping important security updates?
Is the system still able to upgrade other packages?
```

If DNF reports dependency problems, do not force the upgrade without understanding why.

## Practice Lab

Run on a test machine only.

Check available upgrades:

```bash
sudo dnf upgrade
```

Do not confirm yet.

If you see a package you want to skip, answer:

```text
n
```

Then rerun upgrade with an exclude:

```bash
sudo dnf upgrade --exclude=PACKAGE
```

For multiple related packages:

```bash
sudo dnf upgrade --exclude=PACKAGE1,PACKAGE2,PACKAGE3
```

Check what DNF does.

Expected:

```text
DNF upgrades what it can and skips the excluded packages.
```

## Summary

Use temporary excludes when you only need to skip a package once:

```bash
sudo dnf upgrade --exclude=PACKAGE
```

Use permanent excludes or version locks only when there is a strong reason.

Common reasons:

```text
application compatibility
vendor plugin limitations
manual kernel module requirements
temporary testing delay
preventing a downgraded package from upgrading again
```

Main warning:

```text
Excluded or locked packages can create dependency problems.
```

Best practice:

```text
Keep package locks rare.
Review them regularly.
Remove them before large OS upgrades when possible.
```
