# Apwide GoLive Jenkins Pipeline Note

## Context

Apwide GoLive is a Jira plugin used to show which application version is deployed on each environment, for example Dev, TST, STG, or PROD.

The plugin itself is maintained on the Jira side, but Jenkins is involved because some deploy pipelines send deployment information to Jira after deploying an application to OCP.

OCP means OpenShift Container Platform. In this context, Jenkins deploys an application to OpenShift using commands such as `oc` and `helm`.

## Example Jenkins job

Example job found in Jenkins:

```text
MW / cs-player-platform / PAL / DEPLOY-new
```

Example build URL:

```text
https://ci.svc.ifortuna.cz/job/MW/job/cs-player-platform/job/PAL/job/DEPLOY-new/708/
```

This job is a real deploy job. It deploys `playtech-adaptation-layer` to OCP using Helm and then updates Apwide GoLive in Jira.

## Where the pipeline code is

In Replay, the main Jenkinsfile is short and calls a shared library function:

```groovy
mwPlayerPlatformDeployPipeline([
  'APP_NAME': 'playtech-adaptation-layer',
  'HELM_CHART_NAME': './',
  'INCLUDE_HIDDEN_FILES': true,
  'GIT_URL': 'ssh://app-bitb-shared.o.dc1.cz.ipa.ifortuna.cz:7999/mw/ptadapter.git',
  'GO_LIVE_APP_NAME': 'pal'
])
```

This means the job is not implementing the deploy logic directly in the Jenkinsfile. It delegates to the shared library function `mwPlayerPlatformDeployPipeline`.

The most important value for GoLive here is:

```text
GO_LIVE_APP_NAME = pal
```

This is later combined with country codes, so GoLive application names become:

```text
pal-cp

pal-hr
pal-pl
pal-ro
pal-sk
```

The deploy pipeline later calls:

```groovy
mwPlayerPlatformUtils.helmUpgradeParallel(...)
```

That utility is where the country-specific Helm deploys and GoLive update calls are handled.

## Exact call chain

The flow is:

```text
Main Jenkinsfile
  -> mwPlayerPlatformDeployPipeline(...)
    -> stage Initialize
    -> stage HelmChart Checkout
    -> stage Move Image
    -> stage Upgrade release via Helm OCP4
      -> mwPlayerPlatformUtils.helmUpgradeParallel(...)
        -> helmUpgradeStage(...)
          -> helm upgrade ...
          -> goLiveIntegration(...)
            -> apwSetEnvironmentStatus(... status: Deploy)
            -> apwSetDeployedVersion(...)
            -> apwSetEnvironmentStatus(... status: Up)
```

The actual place where GoLive is called is:

```groovy
def goLiveIntegration(targetVersion, application, category, user, buildNumber) {
  try {
    echo "Calling: apwSetEnvironmentStatus with application: ${application}, category: ${category}, status: \"Deploy\""
    apwSetEnvironmentStatus application: application, category: category, status: 'Deploy'

    echo "Calling: apwSetDeployedVersion with application: ${application}, category: ${category}, version: ${targetVersion}, buildNumber: ${buildNumber}, attr:triggered by: ${user}"
    apwSetDeployedVersion application: application, category: category, version: targetVersion, buildNumber: buildNumber, attributes: [
      'Triggered by': user
    ]

    echo "Calling: apwSetEnvironmentStatus with  application: ${application}, category: ${category}, status: \"Up\""
    apwSetEnvironmentStatus application: application, category: category, status: 'Up'
  } catch (err) {
    echo "GoLive plugin integration failed [$err]"
  }
}
```

So the parameters are filled before this function, then passed into `goLiveIntegration()`.

## GoLive/Jira configuration in the pipeline

The deploy pipeline sets these environment variables:

```groovy
environment {
  APW_JIRA_BASE_URL = 'https://jira.myfortuna.eu'
  APW_JIRA_CREDENTIALS_ID = 'jira-cicd-login'
  GOLIVE_ENV_OWNER = 'CS Player Management'
}
```

This means Jenkins talks to Jira/GoLive using the Jenkins credential:

```text
jira-cicd-login
```

In GoLive this appears as the CICD/Jira integration user in the `By` field.

## Which Jenkins parameters matter

There are two related pipelines:

1. Build pipeline: `mwPlayerPlatformBuildPipeline`
2. Deploy pipeline: `mwPlayerPlatformDeployPipeline`

The build pipeline can trigger the deploy pipeline:

```groovy
build job: jobName,
  parameters: [
    string(name: 'IMAGE_TAG', value: imageTag),
    string(name: 'COMMIT_ID', value: commitId),
    string(name: 'TARGET_CLUSTER', value: targetEnv),
    string(name: 'HELM_BRANCH', value: branchName),
    string(name: 'COUNTRIES', value: countries)
  ],
  wait: false
```

In the example, the build pipeline defaults to:

```groovy
def targetEnv = 'tst'
```

So when build triggers deploy automatically, it usually deploys to TST.

The deploy job itself has parameters such as:

```text
IMAGE_TAG
TARGET_CLUSTER
COUNTRIES
COMMIT_ID
DEPLOY_TICKET
HELM_BRANCH
OCP4_BARE_METAL
```

For GoLive, the important ones are:

```text
IMAGE_TAG       -> deployed version
TARGET_CLUSTER  -> target environment, for example TST, STG, PROD
COUNTRIES       -> country/app variants, for example cp, cz, hr, pl, ro, sk
COMMIT_ID       -> build correlation identifier
```

The pipeline also derives:

```text
targetVersion   -> from IMAGE_TAG
goLiveAppName   -> from GO_LIVE_APP_NAME or APP_NAME
targetNamespaces -> for example mw-cz, mw-pl, mw-hr
buildNumber     -> from Jenkins build display name
```

## Exact parameter origin

### Application name

From main Jenkinsfile:

```groovy
'APP_NAME': 'playtech-adaptation-layer'
'GO_LIVE_APP_NAME': 'pal'
```

In `mwPlayerPlatformDeployPipeline`:

```groovy
String appName = callParams.get('APP_NAME')
String goLiveAppName = callParams.getOrDefault('GO_LIVE_APP_NAME', appName)
```

So:

```text
appName       = playtech-adaptation-layer
goLiveAppName = pal
```

Inside `helmUpgradeStage()`:

```groovy
def application = "${goLiveAppName}-${stageName}"
```

`stageName` is the country code from the namespace, for example `cz`.

Final GoLive application:

```text
pal-cz
```

### Countries and namespaces

Default countries:

```groovy
String countries = callParams.getOrDefault('COUNTRIES', 'cp,cz,hr,pl,ro,sk')
```

In `Initialize`:

```groovy
selectedCountries = params.COUNTRIES.split(",")

selectedCountries.each { country ->
  targetNamespaces << "${deployNamespace}-${country.toLowerCase()}"
}
```

`deployNamespace` defaults to:

```groovy
String deployNamespace = callParams.getOrDefault('OCP_NAMESPACE', 'mw')
```

So countries become OCP namespaces:

```text
cp -> mw-cp
cz -> mw-cz
hr -> mw-hr
pl -> mw-pl
ro -> mw-ro
sk -> mw-sk
```

In `helmUpgradeParallel()`:

```groovy
targetNamespaces.each { namespace ->
  String country = countryCodeFromOcpProject(namespace) as String
  deployParallel[country] = helmUpgradeStage(...)
}
```

Country is extracted by:

```groovy
def countryCodeFromOcpProject(String ocpProject) {
  return ocpProject.split("-")[1]
}
```

Example:

```text
mw-cz -> cz
```

### Environment / category

Jenkins deploy parameter:

```text
TARGET_CLUSTER
```

Example from log:

```text
tst
```

In `helmUpgradeStage()`:

```groovy
def category = "${mwPlayerPlatformUtils.getApwCategory(targetEnvironment)}"
```

Mapping:

```groovy
static def getApwCategory(String targetCluster) {
  return [
    'dev'   : 'DEV',
    'tst'   : 'TST',
    'stg'   : 'STG',
    'czprd' : 'PROD',
    'roprd' : 'PROD',
    'hrprd' : 'PROD',
    'plprd' : 'PROD',
    'skprd' : 'PROD',
    'cpprd' : 'PROD',
    'sharedprd': 'PROD'
  ].get(targetCluster)
}
```

So:

```text
tst -> TST
stg -> STG
czprd/plprd/etc. -> PROD
```

This value is sent to GoLive as `category`.

### Version

In deploy pipeline `Initialize`:

```groovy
String[] split = params.IMAGE_TAG.split(":")
targetVersion = split.length > 1 ? split[1] : params.IMAGE_TAG
```

So if `IMAGE_TAG` is:

```text
registry.svc.ifortuna.cz/mw/playtech-adaptation-layer:1.199.0-SNAPSHOT
```

then:

```text
targetVersion = 1.199.0-SNAPSHOT
```

If `IMAGE_TAG` is already:

```text
1.199.0-SNAPSHOT
```

then:

```text
targetVersion = 1.199.0-SNAPSHOT
```

This is used in Helm:

```groovy
sh "helm upgrade ${appName} ${helmChartName} --set image.tag=${targetVersion} ..."
```

And it is sent to GoLive:

```groovy
goLiveIntegration(targetVersion, application, category, getUserInfo(), currentBuild.displayName)
```

Inside `goLiveIntegration()`:

```groovy
apwSetDeployedVersion application: application,
  category: category,
  version: targetVersion,
  buildNumber: buildNumber,
  attributes: [
    'Triggered by': user
  ]
```

### Build number

In deploy pipeline `Initialize`:

```groovy
commitId = params.COMMIT_ID == null || params.COMMIT_ID == '' ? '' : "${params.COMMIT_ID}"
jobName = "${currentBuild.displayName}-${targetVersion}-${commitId}".replaceAll("\\s", "")
currentBuild.displayName = "${jobName}-T"
```

Example final display name from the log:

```text
#708-1.199.0-SNAPSHOT-bc060999-T
```

This is passed as:

```groovy
currentBuild.displayName
```

and then sent to GoLive as `buildNumber`.

### Triggered by

User is collected here:

```groovy
def getUserInfo() {
  wrap([$class: 'BuildUser']) {
    try {
      return "${BUILD_USER} (${BUILD_USER_ID})"
    } catch (error) {
      println "BUILD_USER not supplied, it was most likely triggered from some other pipeline..."
      return "Jenkins"
    }
  }
}
```

Example:

```text
Veic Sanja (veisan)
```

This is passed into:

```groovy
goLiveIntegration(targetVersion, application, category, getUserInfo(), currentBuild.displayName)
```

And sent to GoLive as an attribute:

```groovy
attributes: [
  'Triggered by': user
]
```

### By CICD

This does not come from `getUserInfo()`.

It comes from the Jira credential used for the API request:

```groovy
APW_JIRA_CREDENTIALS_ID = 'jira-cicd-login'
```

The GoLive/Jira API sees the request as being made by this integration user. That is why the GoLive UI shows `By CICD` or the Jira integration user.

### Deployment time

The pipeline does not explicitly send a deployment timestamp in the shown code.

GoLive/Jira creates the deployment time when it accepts the deployment API request:

```text
PUT /rest/apwide/tem/1.1/deployment
```

In the Jenkins log, the response contains fields like:

```json
{
  "deployedTime": 1779785986000,
  "deployer": "JIRAUSER38103"
}
```

That timestamp is then displayed in GoLive Deployment Logs.

## What is sent to GoLive

After Helm deploy, Jenkins calls Apwide GoLive REST endpoints in Jira.

First, it sets the environment status to `Deploy`:

```text
PUT https://jira.myfortuna.eu/rest/apwide/tem/1.1/status-change?application=pal-cz&category=TST
```

Body:

```json
{
  "name": "Deploy"
}
```

Then it writes the deployed version:

```text
PUT https://jira.myfortuna.eu/rest/apwide/tem/1.1/deployment?application=pal-cz&category=TST
```

Example body:

```json
{
  "versionName": "1.199.0-SNAPSHOT",
  "buildNumber": "#708-1.199.0-SNAPSHOT-bc060999-T",
  "description": null,
  "attributes": {
    "Triggered by": "Veic Sanja (veisan)"
  }
}
```

This request body is produced indirectly by:

```groovy
apwSetDeployedVersion application: application,
  category: category,
  version: targetVersion,
  buildNumber: buildNumber,
  attributes: [
    'Triggered by': user
  ]
```

The `apwSetDeployedVersion` function belongs to the GoLive/Jenkins integration. It converts those Groovy parameters into the REST request body sent to Jira/Apwide.

Finally, Jenkins sets the environment status back to `Up`:

```text
PUT https://jira.myfortuna.eu/rest/apwide/tem/1.1/status-change?application=pal-cz&category=TST
```

Body:

```json
{
  "name": "Up"
}
```

## Field mapping

```text
GoLive application     -> application = "${goLiveAppName}-${stageName}", for example pal-cz
GoLive environment     -> category = getApwCategory(TARGET_CLUSTER), for example TST
OCP version            -> targetVersion from IMAGE_TAG
Build number           -> currentBuild.displayName
Who triggered deploy   -> getUserInfo(), sent as attributes["Triggered by"]
Deployment time        -> created by Jira/GoLive when PUT /deployment is accepted
By CICD                -> APW_JIRA_CREDENTIALS_ID = jira-cicd-login
Deployment log         -> created by GoLive after successful apwSetDeployedVersion call
```

## How to verify it in Jenkins

Open a deploy build console log and search for:

```text
apwSetEnvironmentStatus
apwSetDeployedVersion
/rest/apwide/tem/1.1/deployment
/rest/apwide/tem/1.1/status-change
jira-cicd-login
Response Code: HTTP/1.1 200 OK
```

Example log lines:

```text
Calling: apwSetEnvironmentStatus with application: pal-cz, category: TST, status: "Deploy"
Calling: apwSetDeployedVersion with application: pal-cz, category: TST, version: 1.199.0-SNAPSHOT
Calling: apwSetEnvironmentStatus with application: pal-cz, category: TST, status: "Up"
Response Code: HTTP/1.1 200 OK
```

If the response code is `200 OK`, Jenkins successfully sent the data to Jira/GoLive.

## How to validate after Apwide plugin update

Use a non-production deploy, for example TST.

1. Run or observe a real deploy job.
2. Check Jenkins console log for GoLive API calls.
3. Confirm all GoLive requests return `HTTP 200 OK`.
4. Open Jira GoLive for the same application and environment.
5. Verify the version, triggered-by user, deployment time, and deployment log entry.
6. Confirm the final environment status is `Up`.

## Short explanation for colleagues

Jenkins is involved because the deploy pipeline updates Apwide GoLive after deploying the application to OCP. The pipeline gets the version from `IMAGE_TAG`, the environment from `TARGET_CLUSTER`, the application from `APP_NAME` or `GO_LIVE_APP_NAME`, and the triggering user from Jenkins build user information. It then calls Jira/Apwide REST API using the `jira-cicd-login` credential. Jira/GoLive records the deployment log, time, version, and CICD user.

The Apwide plugin upgrade is a Jira-side change, but Jenkins admins should validate that these pipeline API calls still work after the upgrade.
