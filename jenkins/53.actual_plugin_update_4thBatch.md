# Before actual prod deploy:

For prod, prepare the validation before the deploy window by finding representative jobs for each Batch 4 plugin area. Then during the window you only run/open the prepared list.

Before Prod Deploy: Build A Validation List

Search which jobs use Batch 4 plugins on prod:
cd /var/lib/jenkins/jobs
sudo grep -R "<[^>]* plugin=\"" . --include=config.xml \
  | grep -Ei "gradle|maven|junit|javadoc|htmlpublisher|copyartifact|email-ext|mailer|slack|http_request|jira|lockable|parameterized-trigger|promoted-builds|schedule-build|run-condition|conditional-buildstep|git-parameter|extensible-choice|matrix-project|naginator|dependency-check|sonar|subversion"
This gives config files containing those plugin references.

Cleaner version, showing file path + matching plugin:
sudo grep -Rho 'plugin="[^"]*"' /var/lib/jenkins/jobs --include=config.xml \
  | sort -u
Then compare against Batch 4 plugin IDs.

Find jobs by specific plugin. Example for Gradle:
sudo grep -R "gradle@" /var/lib/jenkins/jobs --include=config.xml
For email-ext:

sudo grep -R "email-ext@" /var/lib/jenkins/jobs --include=config.xml
For lockable resources:

sudo grep -R "lockable-resources@" /var/lib/jenkins/jobs --include=config.xml
For copy artifact:

sudo grep -R "copyartifact@" /var/lib/jenkins/jobs --include=config.xml
Convert config path to Jenkins job path.
Example file:

/var/lib/jenkins/jobs/Team/jobs/MyJob/config.xml
Jenkins URL:

https://ci.svc.ifortuna.cz/job/Team/job/MyJob/
For multibranch branch job:

/var/lib/jenkins/jobs/App/jobs/master/config.xml
URL:

https://ci.svc.ifortuna.cz/job/App/job/master/
Create a small validation table before deploy:
Area/plugin       Job URL                         Validation action
Gradle            ...                             Open config, run if safe
Maven             ...                             Open last build, run if safe
JUnit             ...                             Open Test Result page
HTML/Javadoc      ...                             Open published report
Copy Artifact     ...                             Open config or run safe downstream job
email/slack       ...                             Open config, check last notification
lockable          ...                             Open config/run safe job
parameterized     ...                             Open Build with Parameters
Sonar/DepCheck    ...                             Open report/last build
During Prod Deploy: What To Do

After Batch 4 update/restart, check Jenkins starts:
sudo systemctl status jenkins
Check plugin/dependency errors:
sudo journalctl -u jenkins --since "15 minutes ago" --no-pager | grep -Ei "failed loading plugin|failed to load plugin|unsatisfied dependency|dependency errors"
Run safe Jenkins smoke tests:
built-in Pipeline smoke
OpenShift/buildah smoke
nasekatest multibranch scan/build if it exists in prod or equivalent test repo
Open each prepared representative job URL.
For each one check:

job page opens
Configure page opens if you have permission
Build with Parameters opens if applicable
last build page opens
report page opens if applicable
Only run jobs that are safe and approved.
For unsafe jobs, do not run them. Just open config/last build/report pages and confirm no descriptor/form errors.

Check logs after opening/running jobs:
sudo journalctl -u jenkins --since "30 minutes ago" --no-pager | grep -Ei "gradle|maven|junit|javadoc|htmlpublisher|copyartifact|email|mailer|slack|http_request|jira|lockable|parameterized|promoted|schedule|run-condition|conditional|git-parameter|extensible|matrix|naginator|dependency|sonar|subversion|error|exception|failed"
Practical Recommendation

Before prod deploy, do not try to validate every Batch 4 plugin individually. Pick one representative job per area:

1 SCM/multibranch checkout job
1 Maven/Gradle build job
1 JUnit/report job
1 notification job
1 parameterized job
1 lockable/copy-artifact/downstream job if used
1 Sonar/DependencyCheck job if used
That is realistic and useful during a maintenance window.
